# Traffic Dashboard — Agentic Traffic Studio

A standalone web dashboard presenting the same telemetry as the Grafana
"Agentic Traffic Overview" dashboard, behind Keycloak OIDC.

The PromQL is ported verbatim from
`components/nvidia-platform/monitoring/dashboards/agentic-traffic-overview.json`
(see `app/src/lib/queries.ts`), with Grafana's variables resolved to fixed
values: `$__rate_interval` → `5m`, `$az_price_per_gb` → `0.01`, `$namespace` →
`.*`. Both views therefore answer with the same numbers.

## Prerequisites

| Requirement | Why |
| --- | --- |
| `components/auth/keycloak` | Issues the OIDC tokens; generates the client secret |
| `components/nvidia-platform/monitoring` | Provides the Prometheus this queries |
| `components/o11y/beyla` | Source of the L7 RED metrics |
| `components/o11y/network-observability` | Source of the NFM network/cost metrics |
| `components/o11y/tempo` | Source of the service-map edges (metrics-generator `service-graphs`) |
| NVIDIA GPU Operator (DCGM exporter) | Source of the NVIDIA tab in GPU & Accelerators |
| neuron-monitor DaemonSet (`components/o11y/neuron-monitor`) | Source of the AWS Inferentia / Trainium tab; optional, only on Neuron nodes |
| A vLLM deployment | Source of the LLM performance metrics |

Panels whose exporter is missing render an explicit "no data" state rather than
failing — the dashboard is useful with a subset installed.

## Layout

The page is tabbed, one tab per section (At a Glance, Network & Cost, LLM
Performance, Cache Hit Rate, L7 RED, Service Map, GPU & Accelerators, Deep
Links); the definitions live in `src/lib/sections.ts`. The tab strip and the
time-window switcher share a sticky row under the top bar. The active tab is
mirrored into the URL fragment (`#llm`), so section deep links keep working and
Back/Forward move between tabs. Only the active panel is mounted: inactive
panels stop polling Prometheus, and SWR's cache repaints the previous data
immediately when you switch back. Arrow keys, Home and End move between tabs.

### Rearranging panels

Every panel is a portlet (`src/components/PortletGrid.tsx`): hover it and a
grip appears on its top edge, a resize handle in its bottom-right corner. Drag
the grip to move the panel anywhere in the section — the other panels reflow
live and the drop commits (Escape cancels). Drag the corner to change its width,
snapped to the section's 12-column grid, and its height; once a height is set
the chart inside stretches to fill it and tables scroll. From the keyboard, the
grip takes arrow keys to move the panel, Shift+arrows to resize it and Backspace
to restore its default size; double-clicking the corner does the same.

The arrangement is saved per section in `localStorage`
(`ats.layout.v1.<section>`), so it survives reloads on that browser but is not
shared between users. A "Reset layout" button appears above a section whose
layout differs from the default. Panels added in a later release show up at the
end of a saved layout; removed ones are dropped. Below the `xl` breakpoint the
grid falls back to one or two columns and only the order (and height) applies.

## Agents & collectors (header)

Above the tabs sits a health strip for the telemetry pipeline itself. It is
collapsed by default to one row — the heading, state counts (healthy / watch /
degraded / critical / not installed) and chips for only the agents that need
attention — so it takes no space when everything is green. Click the heading
or "Show all" to expand it into one chip per agent or collector the dashboard
depends on, grouped as node agents
(node-exporter, Beyla eBPF, Network Flow Monitor agent, DCGM exporter,
neuron-monitor, the GPU operator DaemonSets, EFS CSI), metrics (Prometheus,
Prometheus Operator, kube-state-metrics, Grafana, Pushgateway, NFM exporter,
metrics-server), traces (the Tempo components) and LLM tracing (Langfuse). Each
chip shows ready/desired from kube-state-metrics; scrape health (`up` for the
component's Prometheus job) and container restarts in the last hour can only
lower the state, never raise it. Hover or focus a chip for the detail, or click
it to pin the detail open (Escape or a click elsewhere closes it). The list
is curated in `src/lib/agents.ts` — it is not a discovery, so a component that
is not installed in a cluster shows as "Not installed" rather than an error;
add or rename entries there to match your install (the workload names follow
the Helm release names this starter kit uses). Pod-to-workload attribution for
the restart count uses the pod-name heuristic in `src/lib/workload.ts`.

## At a Glance

The first tab is a whole-cluster overview: seven blocks of four tiles each,
one block per resource — nodes & pods, CPU, memory, network, storage, GPU &
accelerators, serving (`CLUSTER` and `CLUSTER_THRESHOLDS` in
`src/lib/queries.ts`, plus the fleet-wide `GLANCE`/`KPI` figures). Utilisation
tiles are averages over nodes with a "busiest node" tile next to them, because
an average hides a single saturated node; requested-vs-allocatable only counts
pods in phase Running; network is the nodes' primary NIC (`eth0`), storage is
the Bottlerocket data partition (`/local`) plus kubelet PVC stats. Each tile
(`SignalTile.tsx`) runs one range query over the selected window: the headline
is the latest point, the delta compares it with the window start, and the
sparkline (`Sparkline.tsx`) shows the path; hovering the sparkline shows the
value at that time in the caption. The full KCD Token Factory signal set
stays under LLM Performance and Cache Hit Rate; the per-model / per-pod
breakdown is under GPU & Accelerators.

## Architecture notes

Prometheus is never reachable from the browser. The app proxies every query
through `/api/prom`, which requires an Auth.js session and holds the in-cluster
Prometheus URL server-side. `middleware.ts` puts every route except
`/signin` and the Auth.js endpoints behind authentication.

## Local development

```bash
cd app
npm install
# .env.local — point AUTH_KEYCLOAK_ISSUER at the deployed Keycloak and
# port-forward Prometheus to localhost:9090 first.
npm run dev
```

The realm's `traffic-dashboard` client already allows `http://localhost:3000/*`
as a redirect URI, so no Keycloak change is needed for local work.

`npm run build` runs `scripts/check-client-manifest.mjs` afterwards (`postbuild`).
It fails the build if the `/page` client-reference manifest lists no app client
components — `next build` has exited 0 while emitting such a manifest (see the
note at the top of `EnginesTable.tsx`), and the symptom only shows up at request
time as "Could not find the module ... in the React Client Manifest".

## Service map

`src/components/ServiceMap.tsx` draws east-west connectivity from Beyla's
`traces_service_graph_request_*` metrics (kubelet probe pseudo-clients, named
`i-…` after their node, are excluded — matching the Grafana view). The map is
filterable by namespace, service, AZ, CPU architecture, GPU type and worker
node. Namespace and service are labels on the edge series; the rest are
attributes of the node whose Beyla DaemonSet pod observed the edge (joined via
`kube_pod_info`, with AZ from `kube_node_info`, architecture from
node-exporter's `node_uname_info` and GPU model from DCGM's
`DCGM_FI_DEV_GPU_UTIL`), so they read as "edges with an endpoint on a matching
node". GPU options are present only while GPU nodes exist — they are KEDA-scaled
to zero off-hours. Layout is a dependency-free layered
algorithm in `src/lib/graph.ts` (longest-path layering, barycentre ordering
within a layer) — the graphs here are tens of nodes, so this costs less than a
force-directed library and, unlike one, is deterministic: every ordering
decision breaks ties on the node name, so nodes hold their position and colour
across the 15s refresh.

### Pod drill-down

Clicking a service opens its pods (`src/lib/podGraph.ts` assembles the view):
the services that call it on the left, its pods in the middle, the services
its pods call on the right. Above `POD_GROUP_THRESHOLD` (8) pods the middle
column is one node per AZ — "Group by AZ" / "Show every pod" toggles it — since
the Neuron pools run 16 identical replicas each and 32 dots say nothing three
AZ groups do not. Clicking a neighbouring service re-targets the drill-down;
clicking a group expands it.

Edges in this view come from Tempo's metrics-generator, not Beyla. Beyla's own
service graph stops at service names; Tempo pairs the client span and the
server span of the same request and, with `k8s.pod.name` / `k8s.node.name` as
service-graph dimensions and `enable_client_server_prefix`, emits each edge
with both pods and both nodes
(`traces_service_graph_request_total{source="tempo", client_k8s_pod_name,
server_k8s_pod_name, client_k8s_node_name, server_k8s_node_name}`). The node
pair resolves to AZs through `kube_node_info`, which is what the per-edge and
per-service **cross-AZ share** is computed from — the number a zone-aware
routing decision needs, shown on the service map's edge tooltips as well.
Per-pod rate, errors and p95 are Beyla's server-side RED with scrape and probe
routes excluded. Where Tempo has not paired a hop, the inbound side falls back
to the service total split by each pod's share (drawn dotted, marked as an
estimate) and the outbound side to Beyla's client-side counts on the pod
(exact rate, no error/latency); the tooltip always names the source. Tempo's
pairing window, ingestion slack and store size are tuned for LLM request
lengths in `components/o11y/tempo/values.template.yaml` — see the comments
there before changing them.

Beyla and Tempo emit the `traces_service_graph_*` family under the same metric
names and are told apart by `source` (`beyla` / `tempo`; the latter is a
registry external label in the Tempo values). Every query in `queries.ts` and
both Grafana dashboards select on it — an unqualified `sum()` over the family
double-counts.

Service graphs are not DAGs — Langfuse and its Redis call each other, and a
gateway can call back into the service that called it. Longest-path layering
on a cyclic graph pushes every member of the cycle to the last layer (the
canvas once reached 6,000px wide because of one 2-cycle). The layout therefore
first marks *back edges*: for a mutual pair the lower-rate direction, then any
edge a depth-first walk finds closing a cycle. Back edges are excluded from
layer assignment and barycentre ordering but are still drawn, so the picture
stays complete while the layers stay compact. Empty layers are removed
afterwards so the width tracks the real dependency depth.

Edge colour is health (error ratio under 1% / 1-5% / over 5%), never a series
colour. Because status must not ride on colour alone, unhealthy edges are also
dashed and carry a `!` badge, and the tooltip states the status in words. Edge
thickness and node radius scale with request rate. The drifting dash overlay is
a separate path from the edge stroke so it cannot override the health dash, and
it is hidden entirely under `prefers-reduced-motion` — the arrowheads already
carry direction.

## Cache hit rate

`src/components/sections/CacheHitRate.tsx` treats the vLLM prefix-cache hit
ratio as an SLI in the sense of the KCD Token Factory talk: the cache-hit cliff
shows up in one node, one pool, one tenant or one template version while the
average still looks fine, so the section is built around splits rather than a
headline, and pairs the cause side (hits) with the consequence side (TTFT,
prefill work). Two metric sources feed it:

- **vLLM** (`vllm:prefix_cache_{hits,queries}_total`,
  `vllm:prompt_tokens_cached_total`, `vllm:prompt_tokens_by_source_total`,
  `vllm:request_prefill_kv_computed_tokens`, `vllm:time_to_first_token_seconds`,
  `vllm:kv_cache_usage_perc`, `vllm:num_preemptions_total`,
  `vllm:num_requests_waiting`) scraped by the `vllm-models` PodMonitor. vLLM
  only knows engines, so this gives the **worker node** split (joined to
  `kube_pod_info`; KV cache is node-local, a node that drops alone is a
  routing/placement problem), the **model pool** split (query-weighted hit
  ratio next to token-weighted cached share; a gap means hits land on short
  prefixes only) and the **per-engine diagnosis** table (`CachePodTable.tsx`),
  which applies the rule in `src/lib/cache.ts`: low hits with KV ≥ 85% or
  preemptions is a *capacity bottleneck* (blocks evicted before reuse — lever
  is KV memory, e.g. fp8 KV dtype or replicas); low hits with KV ≤ 60% is a
  *prompt/routing* problem (volatile system prompts, template drift,
  cache-blind routing). Engine age is shown because every restart empties the
  cache.
- **LiteLLM** (`litellm_input_tokens_metric_total`,
  `litellm_input_cached_tokens_metric_total`,
  `litellm_proxy_total_requests_metric_total`) via its Prometheus callback,
  scraped by the authenticated ServiceMonitor in `components/ai-gateway/litellm`.
  The gateway knows the caller, so this gives the **tenant** split
  (`team_alias` / `api_key_alias` of the virtual key, `end_user` from the
  request's `user` field) and the **prompt template version** split
  (`metadata.prompt_template` / `metadata.prompt_template_version` sent in the
  request body, exported through `custom_prometheus_metadata_labels`). Cached
  share = backend `usage.prompt_tokens_details.cached_tokens` / prompt tokens,
  which is why the vLLM pools run with `--enable-prompt-tokens-details`.
  `CacheTenantTable.tsx` joins the three counters per tenant × template × pool.

The Beyla service graph still backs a "callers per model pool" card because it
also sees traffic that bypasses LiteLLM (kgateway, Kong, direct calls).

Two engine caveats the panels cannot hide: the optimum-neuron backend has no
prefix cache at all, so Neuron pools never appear in the cache tables; and
hybrid-attention models (Qwen3.6) cache in 784-token blocks, so prefixes shorter
than that never hit even with `--enable-prefix-caching`.

## GPU & Accelerators section

One section for every accelerator family. The fleet table at the top puts
NVIDIA GPUs (DCGM exporter, keyed by `modelName`) and AWS Inferentia / Trainium
(neuron-monitor DaemonSet from `components/o11y/neuron-monitor`, keyed by
instance family) on the same columns — nodes, devices reported vs. advertised,
devices allocated to pods, average utilisation, memory and a *Serving /
Allocated, idle / Unallocated* state — and a segmented control picks which
family's detail panels render at the bottom. Neuron is a tab here rather than a
section of its own because the question an operator asks first is "is the fleet
busy", not "which vendor". The default tab is whichever family is actually
reporting.

Between the fleet table and the detail panels sit a filter bar and two tables
that span both families:

- **Filter bar** (`AcceleratorFilterBar.tsx`, `src/lib/acceleratorFilter.ts`)
  — Accelerator (NVIDIA GPU / AWS Neuron), Namespace, Service and Tenant, one
  selection driving both tables. Namespace and Service come from the pods
  themselves (the service is the workload name derived from the pod name,
  `src/lib/workload.ts`). Tenant is the LiteLLM team alias with a virtual key
  routed to the pod's model pool (`src/lib/tenants.ts`,
  `litellm_input_tokens_metric_total` by `team_alias, requested_model`), so a
  tenant selection narrows to vLLM engines — a pod no gateway route points at
  has no tenant.
- **Per model & per pod** (`EnginesTable.tsx`, `ENGINES`) — the serving
  signals per model pool and, toggled with "By pod", per vLLM engine pod:
  accelerator utilisation and memory, KV cache, prefix hit, running/waiting,
  generation tok/s, TTFT p95 and tenants. Rows anchor on
  `vllm:num_requests_running` (every engine reports it, GPU or Neuron); NVIDIA
  columns join DCGM on the `pod` label, Neuron columns join neuron-monitor
  through the pod's node via `kube_pod_info`. Model rows aggregate the pods
  that survive the filter: device-weighted utilisation, max KV usage, summed
  counters and the model's own TTFT histogram. Neuron engines show "—" for
  framebuffer, KV cache and prefix hit because those exporters do not report
  them.
- **Per-pod accelerator usage** (`AcceleratorPodTable.tsx`,
  `src/lib/acceleratorPods.ts`, `ACCEL_PODS`) — every pod holding an
  accelerator. GPU rows are one per physical GPU (DCGM, joined on `UUID` with
  the `gpu` index as fallback) with that GPU's memory, power and temperature.
  Neuron rows are one per pod that requested `aws.amazon.com/neuroncore`, with
  the node's core utilisation and device memory; when several Neuron pods share
  a node the figures are the node's and the row is marked `*`. Power and
  temperature are "—" for Neuron because neuron-monitor does not report them.

The Neuron tab (`NeuronSection`, `NEURON` in `queries.ts`) shows NeuronCore
utilisation, device / host memory, execution latency and errors, plus a per-node
table whose state column separates a serving accelerator from one that is
allocated (and billed) but idle. neuron-monitor reports per node and runtime
process, not per pod, so the model pod is joined through `kube_pod_info`.

### NVIDIA tab

Metric names match the repo's `dcgm-metrics.json` Grafana dashboard: fleet
stat tiles, utilisation by pod and temperature per GPU over time (the per-pod
table lives above the tabs, see "Per-pod accelerator usage").

"GPU usage by service" derives a workload name from the pod name
(`src/lib/workload.ts`) because DCGM labels pods, not owners. That is a
heuristic on a naming convention, not an owner-reference lookup, so a pod whose
own name ends in something hash-shaped will be over-trimmed. Utilization is
summed across a workload's GPUs rather than averaged, so a two-GPU workload can
legitimately read above 100% — the GPU count column is what makes that
interpretable.

An empty NVIDIA tab is normal, not a fault: GPU workloads are KEDA-scaled to
zero outside weekday 09:00-18:00 KST, which removes the nodes and their
exporters. The empty state says so.

## Design system

Dark-first. Tokens live in `app/src/app/globals.css` and are mirrored for
Recharts in `app/src/lib/theme.ts`. The rules the charts follow: one axis per
chart (quantities with different units go into separate charts rather than a
dual axis), 2px line strokes, a legend whenever there are two or more series,
colour keyed to the entity rather than its current rank, series beyond the
eighth folded into "Other", text in ink tokens rather than series colours, and
status conveyed by glyph and label as well as colour.
